# 04｜POC 验证与落地交付：证明一个值得继续的变化

本课设计一项有限验证，并说明何时可以进入下一阶段。交付物是 POC 任务书、评测记录、未解决问题和工程交接条件；学习练习不要求部署到真实客户环境。

## 让 POC 回答一个决策问题

开始前先写：“这次结果会帮助谁决定什么？”例如，决定是否继续投入资料核对助手，而不是笼统证明 AI 能做报价。选取一段边界清楚的流程，约定输入、使用者、处理方式、人工复核和异常退出路径。

演示可以用合成材料说明交互；验证需要相应数据与评测设计；正式交付还需要环境、权限、运行维护和责任安排。三者可以连续推进，但不能用演示效果代替后续证据。

## 把技术指标接到业务结果

沿一条链建立指标：**技术方法 → Agent 过程指标 → 中间业务数据 → 最终业务结果**。

例如，字段提取与规则校验影响字段正确率、异常识别和处理失败；这些影响人工复核时间、返工次数和任务通过率；业务层再观察总处理时间、错误损失或服务时效。每一段都是需要验证的因果假设，技术指标提高并不自动保证经营结果改善。

效率应覆盖同一任务边界。辅助流程耗时至少包括准备、模型处理、人工复核、纠错与必要的后续录入；一次性培训和设置成本单列，说明首批与持续使用的差别。将完整人工流程与一段模型响应时间相比，会夸大收益。若教学数据只包含部分环节，结论也必须限定为这些环节。

## 样本与评审怎样安排

样本要覆盖正常、缺失、冲突和异常，而不只选择容易成功的输入。先约定正确答案或可接受标准，再运行方案；调试样本与最终检查样本尽量分开。错误还要按业务后果区分，不能让大量无关紧要的正确字段掩盖关键价格或版本错误。

让实际业务角色参与结果检查，记录谁评、按什么口径评。技术同事确认接口、权限、日志和故障恢复条件。成功标准、投入上限和停止条件应在验证前确定，避免看到结果后修改口径。

## 从验证走向交接

通过 POC 后，逐项确认数据权限、部署环境、配置管理、监控告警、异常人工接管、回退办法、培训与运维责任。解决方案型 FDE 负责把业务验收讲清并组织协作；工程能力不足的部分应由对应负责人承担。

交接记录还要区分“已完成、待验证、下一阶段”。没有实际访问目标系统，就不能写“接口已打通”；在合成案例上算过指标，也不能写成真实客户采用。

## 练习与验收

用[POC 任务书模板](../../templates/04-poc-charter.md)设计一次资料核对验证。读取[教学数据](../../cases/manufacturing-quote/sample-data.csv)及其[口径说明](../../cases/manufacturing-quote/evidence.md)，复算可以计算的结果，列出数据不支持的结论，并安排补证据动作。所有数字仅作为教学演算。

验收看：决策问题是否具体；前后比较口径是否一致；关键错误是否单独检查；是否计算人工负担；结论是否对应继续、调整或停止的动作。常见失败是只报告准确率和“节省时间”，修正时补上分母、样本范围、人工复核及失败处理。

交付物是 POC 任务书与验证结论。完成后用[参考答案](../../cases/manufacturing-quote/reference-answer.md)核对计算与判断，再学习[持续迭代与产品回流](05-adoption-feedback.md)。
