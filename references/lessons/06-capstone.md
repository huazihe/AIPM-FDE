# 06｜综合项目：把五份成果连接成一次交付判断

本课将前面的成果串成可评审的方案。目标是证明你能从材料出发，提出有限判断，组织验证，并在新证据出现后修订决定。完成课程练习不等于取得职业认证，也不代表已经完成真实企业交付。

## 项目任务

阅读[合成案例任务](../../cases/manufacturing-quote/brief.md)，先明确当前可用证据与限制，再完成五份成果。可以使用已有练习结果，但需要整体回读，消除不同阶段之间的矛盾。

| 成果 | 必须回答的决定 | 模板 |
|---|---|---|
| 调研简报 | 进入现场优先核实什么 | [调研简报](../../templates/01-research-brief.md) |
| 需求诊断卡 | 哪个问题值得验证，商业条件到哪一步 | [诊断卡](../../templates/02-diagnosis-card.md) |
| 业务模型与方案 | 规则、责任和边界如何约定 | [Ontology 与方案](../../templates/03-ontology-spec.md) |
| POC 任务书与结论 | 结果支持继续、调整还是停止 | [POC 任务书](../../templates/04-poc-charter.md) |
| 采用与回流记录 | 接下来观察什么，哪些方法可以复用 | [采用与回流](../../templates/05-adoption-feedback.md) |

没有真实上线条件时，第五份成果应提交观察计划和已有反馈分类，不能虚构使用结果。案例中的合成数据只能支持教学演算，所有结论保留这一适用范围。

## 做一次跨阶段走读

选择一条最重要的业务问题，从证据一直追到方案、规则、评测与后续动作。每次跨阶段都问：上一份材料支持这一步吗？有哪些假设被悄悄补成了事实？如果关键证据被推翻，下游哪些内容需要一起改？

例如，方案声称减少报价总周期，但评测只测量字段录入时间，就需要收窄结论或补充覆盖等待、核价和审批的观察。只修改总结里的一个数字，无法修复证据范围与业务承诺之间的错位。

演示时也要展示异常路径。让评审者看到资料缺失、版本冲突和无法确认规则时，系统及人员如何处理。正常流程展示能力，异常流程展示你是否理解实际交付条件。

## 评审方式

依照[成果评审标准](../rubric.md)，按业务理解、证据使用、业务建模、验证设计、采用与回流五个维度给出“可继续 / 需修改 / 证据不足”的判断。每个判断都要指出产物中的具体位置，并给出最小修订或补证动作，不以文字多少或演示美观替代质量。

以下问题需要先修订再通过相应部分：用假设冒充客户事实；计算口径无法复核；关键规则和责任无人确认；把 Demo 写成已部署；把合成结果写成真实业绩。缺少采购证据可以保留，但必须改变推进结论，不能靠技术表现填补。

## 再做一次跨场景迁移

默认使用[报告审核迁移案例](../../cases/transfer-challenge.md)，也可以自选客服工单、合同审阅或其他熟悉业务。只迁移判断方法，写一页说明：五步主线哪些部分可保留，业务对象、风险、评测口径和决策角色分别要怎样变化。

例如，报价中的版本追踪方法可以帮助报告审核，但“正确”的判定者、错误后果和人工批准条件不同。把报价字段换成报告字段还不算完成迁移，需要说明变化为何影响方案与验收。

## 完成与下一步

最终提交五份成果、一次跨阶段走读记录和一页迁移说明。学习者应能解释关键取舍，指出当前证据支持什么、不支持什么。若评审发现问题，应能独立修订并解释修改依据；已符合标准的作品无需为练习而制造错误。AI 可以协助起草，但结论需要学习者理解并确认。

可先完成初稿，再对照[参考答案](../../cases/manufacturing-quote/reference-answer.md)；需要示范时也可以直接阅读。参考答案是一条可行路径，不是唯一解；不同方案只要有一致证据、明确边界和可执行验证，同样可以成立。将未解决能力缺口记录为下一轮练习目标，真实项目经验则另以授权材料、使用记录与验收结果积累。
