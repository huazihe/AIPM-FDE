# 共修｜GitHub：把需求、修改和验收接起来

本课面向懂产品工作、尚未熟悉 GitHub 协作的人。目标是读懂 AI 或研发交付了什么，知道哪里提出问题、哪里查看修改、何时可以接受结果。你可以把具体命令交给 Agent，但需要自己确认目标仓库、修改范围和验收证据。

## 六个词放进同一件事

假设团队要修正一份 POC 任务书：旧版本只写“准确率达到要求”，没有说明样本、分母和关键错误。一次完整协作可以这样发生：

| 词 | 在这个任务中的含义 |
|---|---|
| Repository / repo，仓库 | 任务书、案例、脚本及修改历史共同存放的项目空间 |
| Issue，议题 | 记录现象、影响、证据和期望，例如“验收标准缺少关键错误定义” |
| Branch，分支 | 为这次修改单独工作，便于检查，也减少与他人工作混在一起 |
| Commit，提交 | 保存一组有说明的文件改动；说明应让人知道为什么改 |
| Pull Request / PR，合并请求 | 请团队审阅这组改动，讨论是否纳入目标分支 |
| Fork，派生仓库 | 在自己账号下建立与来源保持关系的副本，便于独立修改和协作 |

Commit 不等于已经发布；PR 打开也不等于修改已被接受。团队审阅后执行 merge，才把修改合入指定分支。是否随后部署网站，取决于该仓库的发布配置；**merge 不天然等于上线**。测试完成、代码合并、部署成功和客户开始使用，应分别报告。

## 产品经理最该读的是 diff

Diff 展示旧内容被怎样修改。审阅任务书时，不只看标题“补充验收标准”，还要逐行确认：有没有删除原有人工审核？有没有把待验证目标改写成已完成效果？有没有夹带客户数据或无关文件？

例如，一次合理修改可以把“效果好即可”替换为“在约定样本上分别记录字段正确率、关键错误和人工复核时间”。如果同时新增“已为客户节省一半成本”，却没有来源，就应要求删除或补证据。提交说明写得清楚，不能代替对实际差异的检查。

Issue 也不只是让研发领任务。它能把业务表达变成可追踪的问题：谁在哪一步受影响、怎样复现、期望行为是什么、哪些范围暂时不做。PR 则应说明实现了哪部分、怎样验证、仍有什么限制。用两者关联需求与交付，可以减少口头承诺丢失。

## 练习与验收

用本课程的 [POC 模板](../../templates/04-poc-charter.md)，写一份本地模拟 Issue：指出一个具体待改项，补上现象、影响、期望和验收方式。再假想一个 PR，描述最小修改，不要求真的联网发布。

你应能说明仓库、分支、提交、PR 和发布的区别，并从差异中发现越界改动。熟悉这些概念后进入 [第一个 Issue 与 PR](github-first-pr.md)；如果你已在团队中熟练使用，可直接回到 [需求整理与诊断](../lessons/02-discovery-diagnosis.md)，练习把现场需求写成可执行议题。
