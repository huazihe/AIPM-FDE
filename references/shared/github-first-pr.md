# 共修｜完成第一个 Issue 与 PR

本课用一个小修改走完“提出问题—修改—检查—审阅”的过程。练习目标是留下可追溯证据，而不是累计提交次数。默认先在本地练习；你明确选择真实 GitHub 实操时，使用你自己拥有或获准写入的练习仓库，不自动向本课程仓库提交内容。

## 先选一个足够小的任务

推荐任务：在练习仓库中新增一页“POC 验收应怎样记录”，写清样本范围、指标口径和未验证项。只用合成材料，不搬运真实客户记录。若没有仓库，可以先在新建的本地练习目录完成同样的文档和差异检查；这只能记为本地演练，不能写成已开 Issue 或 PR。

真实实操开始前，确认账号、目标仓库、可见范围和本轮授权。若已明确授权完整的建分支、推送和开 PR 练习，就沿该范围执行，不反复确认；授权没有包含合并、发布或删除时，停在相应边界。

## 一次完整的操作路线

1. **提出问题。** 新建 Issue，说明原有验收描述缺什么、影响谁，以及本次完成标准。题目可写“补充 POC 样本与人工成本口径”。不要用“优化一下”代替问题。
2. **建立独立分支。** 在确认过的基线创建工作分支；先看现有改动，避免将其他人的文件混进练习。
3. **完成最小修改。** 新增或修改目标文档，只处理 Issue 约定范围。引用本地相对链接，保留“教学假设”和“待验证”等必要状态。
4. **检查并提交。** 请 Agent 展示 diff、检查链接并列出将提交的文件。确认没有密钥、客户信息、学习存档或无关改动，再记录提交。
5. **推送并创建 PR。** 在已有授权范围内推送分支，打开指向正确目标分支的 PR，关联 Issue，写明变化、验证和剩余限制。
6. **做一次审阅。** 从读者角度打开文件和差异，提出一条有依据的意见并修正。不要为了练习假造问题。
7. **记录结果。** 保存 Issue、PR 和提交的链接以及当前状态。是否合并按会话授权和仓库规则执行；是否部署另看发布配置与运行结果。

## PR 描述示范

> 原验收说明未定义样本范围，容易把少量演示误当成完整验证。本次补充样本来源、关键错误和人工成本的记录方式，并保留尚未验证的项目。已检查文件链接及差异；本次未运行真实客户试点。

这段说明让审阅者知道问题、改动和证据。比“完成优化，效果很好”更容易验收，也不会把文档编辑夸大成业务成果。

## 完成条件与回到业务

真实练习完成时，应有可打开的 Issue 和 PR、范围一致的 diff，以及与实际状态相符的记录；本地练习则交问题说明、修改前后对比和检查记录。两种完成情况分开标记。

下一步将这个过程用于 [POC 验证与交付](../lessons/04-poc-delivery.md)：问题有来源、改动有边界、结果可复查。上线后的 Bug、需求变化和使用障碍，再按 [持续迭代与产品回流](../lessons/05-adoption-feedback.md) 分别建立处理记录。
