# 成果评审标准

评审对象是作品中的判断与证据，不是学习者的身份或资历。以下标准用于教学，不构成职业认证。

## 三种评审结论

- **可继续**：当前决策有必要证据，尚未知部分明确且不会被误当成结论；下一阶段能据此工作。
- **需修改**：已有证据足够，但结论、范围、规则或责任与证据不一致；指出具体修改位置。
- **证据不足**：缺少必要材料或观察，暂时无法判断；提出最小补证动作与负责角色。

未作答的维度记“未评审”，不能填高分，也不能凭空判学习者不适合岗位。非关键问题不阻塞整体学习；影响下一阶段的关键问题需要先补齐或缩小练习范围。

## 五份成果的通过条件

| 成果 | 必须看见的证据 | 常见退回原因 |
|---|---|---|
| 调研简报 | 信息日期与来源；事实/推断/未知分开；现场待确认事项 | 把企业宣传或规模当成痛点证据 |
| 需求诊断卡 | 真实工作链、角色与交接；主假设与反证；痛/值/买分别判断 | 老板的愿望直接变成需求；问价等同成交 |
| Ontology 与方案 | 对象关系；字段来源/单位/空值/版本；规则的条件、动作、责任与例外 | 只有数据库字段；“按经验处理”没有适用边界 |
| POC 章程与交接 | 基线、样本、预期阈值、失败模式、人工复核、停止条件与工程负责人 | 只展示成功样例；Demo 通过便写可上线 |
| 采用与回流记录 | 真实项目有使用分母和效果证据；纯教学练习有反馈分类、观察计划与候选复用边界 | 账号数当活跃用户；编造采用结果；共性出现即自动升级产品需求 |

尚未上线的项目可以提交观察计划；这只能证明采用方案已设计，不能记录为客户已经采用。纯教学练习不以取得真实运营数据作为通过条件。

## 综合一致性

评审五份成果之间是否能追溯：同一主问题、同一对象口径、同一数据范围，方案对应诊断，评测对应业务目标，反馈对应验收边界。

技术指标与业务指标之间应有可解释的因果假设，但不能仅凭相关变化断言因果。小样本节时不能直接外推全年现金收益；未释放的工时也不等于节省了人力预算。

允许多个合理方案：规则明确、风险较低时可以优先确定性程序；材料语义复杂时可以使用模型辅助并保留复核。不要求所有环节都上 Agent。

## 反馈写法

每次反馈给出：作品位置 → 证据或缺口 → 对决策的影响 → 最小修改或补证动作。优先处理会导致错误承诺、错误计算、错误权限或错误上线的事项，再改表达。

示例：

> 你的 POC 章程把“首次字段正确率”写成了自动发送报价的上线门槛。案例仍存在版本冲突与规则例外，因此这个指标只能支持辅助整理的判断。请将自动发送移出本轮范围，加入版本核对、复核责任和异常退回路径。

## 迁移检查

换到 [报告审核场景](../cases/transfer-challenge.md) 后，学习者应能保留证据分层和五步结构，重新定义对象、角色、错误成本与验收指标。照搬制造业字段或审批阈值视为未完成迁移。
